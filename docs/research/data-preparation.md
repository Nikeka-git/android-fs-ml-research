При подготовке производных данных сохранять `report_id`, хеш родительского текста, версию преобразования и происхождение разметки. Не переносить ожидаемую метку, ответ проверяющего или результат будущего выполнения во входные признаки.

## Порядок подготовки

1. Проверить закреплённый URL, размер и SHA-256 исходных байтов. Несовпадение останавливает подготовку; запись не исправлять автоматически под новый источник.
2. Отделить справочные аннотации от текста, который получает парсер. Сохранить исходную копию и описание преобразования; не менять диагностический контекст ради совпадения с меткой.
3. Нормализовать выходы в единую схему: ID источника, диагностическая категория, контекст файловой системы, версия парсера и причина отсутствующего результата. Неизвестное значение хранить отдельно от отрицательной метки.
4. Выявить точные дубликаты по SHA-256. Производные одного файла и семантически связанные случаи объединить до разделения данных; сходство по происхождению требует отдельной проверки и не определяется одним хешем.
5. Независимо просмотреть спорные метки, сохраняя исходную версию, решение и основание изменения. Ручные программные тесты хранить отдельно от исследовательских наблюдений.
6. Зафиксировать версию реестра и проверить её командой ниже. Закрепить фактическое разбиение отдельным манифестом до оценки новых моделей.

## Разделение и ограничения

В Assignment 3 описаны 6/2/4 исходных файла и 768/256/512 производных строк для train/validation/test. Перечень ID в каждой части и сами строки в предоставленном документе отсутствуют, поэтому в новом реестре `partition` остаётся `null`. Назначать эти ID задним числом нельзя. Все 12 текстов использовались при разработке правил парсера; совпадение на них является проверкой разработки, а не независимой оценкой обобщения.

Для последующих исследований единица разделения — исходный файл вместе со всеми потомками. При переходе к случаям дефектов нужна более строгая группировка по общей линии происхождения (`lineage_id`): связанные отчёты, исправления и производные одного случая не должны попадать в разные части. Предобработка обучается только на тренировочных данных; параметры выбираются по validation; test используется после фиксации решений. Текущий корпус мал и несбалансирован; перенос выводов на ACK, Android-устройства и файловые системы требует новых данных.

## Проверка материалов

Из корня репозитория, Python 3.12 или новее, стандартная библиотека:

```text
python tools/verify_research_sources.py
python tools/verify_research_sources.py --fetch
```

Первая команда проверяет структуру реестра, локальные копии документа и схемы. Вторая дополнительно загружает 12 закреплённых публичных текстов и проверяет размеры и SHA-256. Команды не выполняют содержимое входов. Проверка источников не запускает диагностический парсер, ML-прототип или Android-код.

Смысл показателей, правила сравнения и условия принятия выводов описаны в [методике оценки](evaluation-methodology.md). Состояние индивидуального вклада отражено в [сведениях о команде](../team.md).
